The three git commands

Every change, no matter how small, ends with these three. Run them from the terminal in VS Code, inside the website folder.

> git add -A # 1. gather up everything you changed
> git commit -m "Fix the About page typo" # 2. save it with a note
> git push # 3. send it to GitHub

Think of it as gather, save, send. Nothing leaves your computer until step three.

Two more worth knowing:

> git status # what have I changed so far?
> git pull # get anyone else's changes before you start

git pull matters the moment more than one person touches the site. Run it before you begin, not after.

If a file called COMMIT_EDITMSG opens, nothing is broken.

You ran git commit without a message, so git opened an editor to ask for one. That tab is the message box. Type your message on the very first line, above all the grey # lines, then Ctrl+S to save and Ctrl+W to close. The commit finishes as the tab closes. Closing without saving cancels it.

Using -m "your message" as above avoids it entirely.

The same thing by clicking

Ctrl+Shift+G opens the Source Control panel. The three steps are the same, and always in this order:

  • Stage. Your changed files sit under Changes. Click the + beside one to move it into Staged Changes, or the + on the Changes heading to take all of them. Staging is you saying "this one goes in".
  • Commit. Type your message in the box at the top of the panel, then Ctrl+Enter. Type it in the box and git never needs to open that editor file.
  • Push. The button underneath turns into Sync Changes with a number on it. That number is how many commits are waiting. Click it.

The one trap is committing with the message box empty, which is what sends you to COMMIT_EDITMSG.

Setting up, once per computer

  1. Get the code

    > git clone https://github.com/SnehaJain-bd/snehajain.co.uk.git

  2. Install what it needs

    From inside the folder. Once, and again only if someone adds a new package.

    > npm install

  3. Run it locally

    Opens at localhost:3000 and updates as you type. Leave it running while you work.

    > npm run dev

If PowerShell refuses to run npm, saying scripts are disabled on this system, that is Windows blocking scripts by default. Fix it once:

> Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

It affects only your user account. Or skip it and type npm.cmd instead of npm every time.

Adding pictures to a project

  1. Drop the full-size originals in

    Into source-images/<project>/. Never into public/. Originals are deliberately kept out of the repo, because git keeps every version of every file forever.

  2. Shrink them

    Caps them at 2000px and writes web-sized copies into public/work/<project>/.

    > npm run images

  3. Gather, save, send

    That is it. You do not tell the case study about the new picture. The folder is the gallery.

The filename does the work

Three things are decided by what you call the file, so name them properly.

FilenameWhat it does
cover.jpgThe big image at the top, and the card on the work page
01-storefront.jpgGoes in the gallery. Numbers keep them in order
02-fridge-wide.jpgThe word wide makes it span the full width
cover-attention.jpgCrops the cover to the busiest part rather than the centre

The rest of the name becomes the alt text a screen reader announces, so pattern-detail.jpg is read aloud as "Asmi, pattern detail". Numbers and the word wide are stripped out of that automatically. Renaming a file reorders the page.

Exporting: what actually matters

The pipeline handles resizing, compression and format. These are the things it cannot fix for you, so they have to be right on the way in.

  1. Never upscale

    This is the only one that cannot be undone. Enlarging a small export invents pixels that carry no detail, and no amount of processing gets it back. A 4096px file exported from a 1000px original is worse than the 1000px original, because it is four times the size and exactly as soft.

    The tell is file size against dimensions. A genuine 4000px photograph is several megabytes. If a 4000px file is under half a megabyte, it has been upscaled.

  2. Export at 2000px on the long edge, or larger

    2000px is where the pipeline caps, so anything above that is trimmed and anything below is served at whatever it is. Retina screens draw two device pixels per CSS pixel, which is why a 1000px image looks soft in a 1000px slot.

    Larger than 2000 is fine and costs you nothing, since it never reaches the repo.

  3. Give the cover room to be cropped

    Covers are cropped to 3:2. Anything important near the top or bottom edge will be cut, so leave space around the subject rather than filling the frame. If the composition cannot survive that, name the file cover-attention.jpg and the crop finds the busiest part instead.

  4. Export in sRGB

    Not Adobe RGB or Display P3. Browsers assume sRGB when a file has no profile, so a wide-gamut export renders flat and slightly grey. If your reds look muted on the live site but fine in Illustrator, this is why.

  5. PNG for flat colour, JPEG for photographs

    Packaging renders, logos, anything with large areas of one colour: PNG. Photographs and anything with gradients or grain: JPEG at high quality. The pipeline converts everything to JPEG for the web anyway, so this is about giving it a clean original rather than one that has already been through lossy compression once.

Do not put words inside an image. Text baked into a picture cannot be read by a screen reader, cannot be found by search, does not resize with the rest of the page, and goes blurry on the exact screens where type should be sharpest. A pack shot with the brand name on the packaging is fine, that is the product. A caption or a heading set inside a JPEG is not.

Rough weights to expect

After npm run images, a 2000px file lands somewhere between 50 KB and 500 KB depending on how much detail it holds. A flat packaging render compresses to almost nothing; a busy photograph with texture does not.

  • Under 30 KB at 2000px usually means the source was upscaled or already over-compressed.
  • Over 600 KB is worth a look. Usually it is noise or film grain, which compresses badly and is rarely doing any work at web size.
  • The whole of public/work/ is around 7 MB for five projects. If that doubles without the number of projects doubling, something went in at the wrong size.

Alt text, in one line

The filename becomes the alt text, so name files as though describing them to someone on the phone. strawberry-tub.jpg is good. IMG_4471.jpg is read aloud exactly as it looks. Purely decorative images should have empty alt text rather than a description, but nothing in public/work/ is decorative: it is all the work.

Adding a whole project

A project is two things with the same name: a file of words, and a folder of pictures.

  1. Copy an existing case study

    Any .mdx in content/projects/. Rename it in lowercase with hyphens, no spaces. The filename becomes the web address, so swirly.mdx is /work/swirly.

  2. Change the block at the top and write the body

    There are no image paths in it. Nothing to keep in step with the folder.

  3. Make the matching pictures folder

    source-images/<same-name>/, then npm run images.

  4. Gather, save, send

If you write the words before the pictures exist, nothing breaks. The project quietly stays off the site and the build log tells you which folder it is waiting for.

The switches at the top of a case study

  • order sets its position on the work page, lowest first.
  • published: false takes it off the site completely but keeps the file. No page, no card, and no dead links, because it drops out of the "next project" chain too. This is how you park something.
  • featured: false keeps it off the home page only.
  • client is optional. Leave the line out and the "For ..." line and the Client row both disappear. Same for year, sector and services. An empty field is never printed as a blank row.

Writing, pictures, writing, pictures

In a case study, ## starts a section and a blank line separates paragraphs. <Gallery /> on a line of its own drops the pictures in.

One <Gallery /> shows the whole folder, which suits a case study that is one piece of writing followed by the work. To build an argument instead, name the files each block should show:

## The brand
 
Rooted in a blend of cultural symbolism and modern design.
 
<Gallery pick="box, pattern detail" />
 
## Bridging culture with contemporary expression
 
The identity merges tradition with modern sensibilities.
 
<Gallery pick="label tag wide" />
 
## A distinctive identity
 
It tells a story.
 
<Gallery />
  • A name is just the filename, no path and no .jpg. Capitals, spaces, hyphens and underscores all work, so pattern detail finds pattern-detail.jpg.
  • The order you write them is the order they appear.
  • A bare <Gallery /> shows whatever no pick has claimed. Leave one at the end and new photographs appear there on their own, without you editing the case study again.
  • Each block lays out its own rows, so a pick of two sits side by side and a pick of one runs full width. That is your layout control.
  • Misspell a name and the build stops and lists what is actually in the folder. Better to catch it there than to find a missing gallery weeks later.

Before you send it

Two checks, both worth the minute they take.

  1. Look at it

    npm run dev, then open localhost:3000. This updates as you type, so it is usually already open.

  2. Prove it builds

    This is the exact command Vercel runs. If it passes here it will pass there, and a broken build caught on your own machine costs nothing.

    > npm run build

After you push

  • Vercel notices the push and rebuilds on its own. There is no deploy button and nothing to upload.
  • Every branch gets its own preview link. main is the live site.
  • If the build fails, Vercel emails you and the site stays exactly as it was. A bad push cannot take the site down, it just does not replace it.
  • Read the failure from the top. The first error is the real one, the rest is noise.

When it goes wrong

I want to undo what I just changed, before committing

Throws away your edits to that file and puts back the last committed version. There is no undo for this, so be sure.

> git checkout -- path/to/the/file
I committed but have not pushed, and want the message back

Undoes the commit and leaves every change sitting in your folder untouched, ready to commit again.

> git reset --soft HEAD~1
git says the push was rejected

Someone else pushed first. Pull their work, then push again.

> git pull
> git push
A picture is not showing up

Almost always one of two things: the original went into source-images/ but npm run images was never run, or it was run but the result in public/work/ was never committed. Run git status and see what is sitting there unstaged.

Removing a picture

Delete it from both places, source-images/<project>/ and public/work/<project>/. Only the second one is in the repo, so only deleting the first changes nothing.
